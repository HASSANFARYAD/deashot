# P0 — Critical

### P0-1 · Shoot origin is never validated → free aimbot
`apps/game-server/src/rooms/TeamDeathmatchRoom.ts:394-433`

The client supplies `ox, oy, oz` and the server uses them verbatim as the ray origin. Fire rate, ammo, alive and phase are validated; **geometry is not**. A modified client sends an origin 0.1 m from any enemy's head with a direction pointing at it and lands a guaranteed headshot from anywhere on the map, at the full 600 RPM. Spec `0005-combat.md:8` claims the server "validates every shot".

**Fix.** Stop trusting the client origin entirely — reconstruct it:

```ts
const origin = { x: p.x, y: p.y + EYE_HEIGHT, z: p.z };
```

Then validate direction against the player's own synced `yaw`/`pitch`, which the server already has:

```ts
const [lx, ly, lz] = lookVector(s.yaw, s.pitch);
if (lx * dx + ly * dy + lz * dz < Math.cos(stats.spread + AIM_TOLERANCE)) return;
```

Keep the client-supplied origin only as a sanity signal: if it is more than ~0.75 m from the reconstructed origin, log it as a cheat signal.

### P0-2 · Hitscan ignores all world geometry → shoot through walls
`TeamDeathmatchRoom.ts:517-548` (`raycastPlayerCapsule`)

The server's raycast tests **only player capsules**. It has no knowledge of the 4 outer walls or 11 cover blocks defined in `apps/web/src/game/map/ArenaMap.ts`. Every shot with line-of-sight fully blocked still registers damage. Cover is decorative.

**Fix.** Move the collider list out of `ArenaMap.ts` into `packages/game-config/src/map.ts` as data (`MAP_COLLIDERS: AABB[]`), add `raycastAABB()` to a shared module, and in `handleShoot` compute `tWall` first, then discard any player hit where `hit.t > tWall`.

---

### P0-3 · Server simulates no world collision → players clip through everything
`TeamDeathmatchRoom.ts:378-390`

The server's entire collision model is `if (p.y < 0) p.y = 0` plus a `±48` clamp on x/z. The client runs full AABB resolution (`CollisionWorld.resolve`). Consequences:

- Server-authoritative positions land **inside** solid cover blocks.
- Client and server disagree by more than `RECONCILE_TOLERANCE` (0.5 m) any time you touch geometry → continuous snap-back near every wall.
- Combined with P0-2, a player standing inside a pillar is visible and shootable by the server, invisible to the client.

**Fix.** Same shared module as P0-2 — run the *identical* `resolve()` function on both sides. This is the root cause of most reconciliation churn in the project.

### P0-4 · Room tuning options are client-controlled
`TeamDeathmatchRoom.ts:129-143`

`onCreate(options)` accepts `killLimit`, `duration`, `warmupPlayers` and `warmupSeconds` straight from the join payload. Any browser console can do:

```js
client.joinOrCreate("tdm", { killLimit: 1, warmupSeconds: 1 })
```

and win a match with one kill. The integration tests (`test-combat.cjs:56`) rely on exactly this path, so the hole is deliberate — but it ships to production.

**Fix.** Gate the overrides:

```ts
const testMode = process.env.ALLOW_TEST_ROOM_OPTIONS === "1";
if (testMode) { /* apply opts */ }
```

Set it in `run-integration.cjs` only. Alternatively register a separate `tdm-test` room definition that `index.ts` only defines when `NODE_ENV !== "production"`.

### P0-5 · Auth is optional and the default JWT secret is committed
`TeamDeathmatchRoom.ts:91-112`, `apps/api/src/index.ts:28`, `docker-compose.yml:8`

Four compounding problems:

1. `static onAuth()` **mints a random guest identity when no token is supplied**. The JWT gate is opt-in — connect without a token and you get a server-trusted identity anyway.
2. Both services fall back to the literal `"deashot-dev-secret-change-me"` when `JWT_SECRET` is unset.
3. `docker-compose.yml` hardcodes that same value, so a default deploy uses a secret published in the repo. Anyone can forge a token for any username.
4. Issued tokens have **no `expiresIn`** — they are valid forever.

**Fix.**

```ts
const SECRET = process.env.JWT_SECRET;
if (!SECRET && process.env.NODE_ENV === "production") {
  throw new Error("JWT_SECRET is required in production");
}
```

Require a token when `process.env.REQUIRE_AUTH === "1"`; add `{ expiresIn: "12h" }` to `app.jwt.sign`; change compose to `JWT_SECRET=${JWT_SECRET:?set JWT_SECRET}`.

### P0-6 · `pnpm lint` is broken and CI never runs it
`apps/web/package.json:16`, `.github/workflows/ci.yml`

`"lint": "eslint src/"` — but `eslint` is in no `devDependencies`, there is no `eslint.config.js` anywhere, and the CI pipeline runs typecheck → build → unit → integration with **no lint step**. So the failure is invisible. `AGENTS.md` lists `pnpm lint` as a standard command.

**Fix.** Add `eslint`, `typescript-eslint`, `eslint-plugin-react-hooks` to `apps/web`, add a flat config, and insert into CI between Typecheck and Build:

```yaml
- name: Lint
  run: pnpm lint
```

Note that `react-hooks/exhaustive-deps` would *not* have caught P1-16 on its own — `settings.sensitivity` is genuinely read inside that effect, so the dependency is "correct" by the rule's definition even though including it is the bug.

### P0-7 · Docker deployment does not exist
`docker-compose.yml`

The compose file builds `./docker/api`, `./docker/game-server` and `./docker/web`. **That directory is not in the repo.** `infra/docker/` and `infra/nginx/` exist but are empty. `docker compose up` fails on the first service. README and `AGENTS.md` both list Docker as complete in Phase 0.

**Fix.** Either write the three Dockerfiles under `infra/docker/` and repoint compose, or mark Docker as not-yet-implemented in README/PLAN so the claim stops being false.

### P0-8 · Game server URL is hardcoded to localhost
`apps/web/src/game/networking/GameSocket.ts:121`

```ts
this.client = new Client("ws://localhost:2567");
```

`VITE_SERVER_URL` is declared in `.env.example` and typed in `vite-env.d.ts`, but read nowhere. The built client can only ever talk to a server on the developer's own machine. (The `/ws` proxy in `vite.config.ts:8-13` is also dead — nothing uses that path.)

**Fix.** `new Client(import.meta.env.VITE_SERVER_URL || "ws://localhost:2567")`, and delete the unused proxy block.

# P1 — Major

### P1-9 · Hit markers and damage indicators fire for the whole room
`TeamDeathmatchRoom.ts:462,471` · `GameEngine.ts:245-253` · `GamePage.tsx:56-79`

The server `broadcast()`s both `"hit"` and `"damage"` to every client (`{ except: [] }` is a no-op), and the client forwards them without checking `attackerId === myId` / `targetId === myId`. **Every player sees a hit marker every time anyone hits anyone**, and a red damage flash every time anyone takes damage. In an 8-player match at 600 RPM the HUD is permanently lit. It also leaks who is engaging whom.

**Fix.** Server: `this.clients.find(c => c.sessionId === sessionId)?.send("hit", …)` for the shooter, and the same targeted send to the victim for `"damage"`. Keep `"kill"` as a broadcast (the kill feed is public). Add the `myId` guard client-side as defence in depth.

---

### P1-10 · ADS movement desyncs client from server
`PlayerController.ts:61,75` vs `TeamDeathmatchRoom.ts:355-371`

The client multiplies both acceleration and max speed by `PLAYER_AIM_SPEED_FACTOR` (0.65) while aiming. The server does not — **`aim` is not a field in `PlayerInput` at all**. Holding right-click makes the client 35% slower than the server's simulation, so the two diverge past the 0.5 m tolerance in about a quarter second and the player is snapped forward, repeatedly, for as long as they aim.

**Fix.** Add `aim: boolean` to `PlayerInput` (`packages/shared/src/protocol/input.ts`), send it from `GameEngine.loop`, and apply the identical factor in `onTick`.

---

### P1-11 · Stale input replays forever
`TeamDeathmatchRoom.ts:147-160,282` · `GameSocket.ts:213-217`

`this.inputs` is written on every `"input"` message and cleared **only in `onLeave`**. The tick loop reads whatever is in the map. If a client's connection stalls, its tab is backgrounded (`setInterval` throttling), or its input timer dies, the server keeps re-applying the last received input at 60 Hz — a player who lags out mid-strafe keeps sliding across the map under server authority.

**Fix.** Store `receivedAt` alongside each input and treat it as neutral after ~250 ms:

```ts
const input = this.inputs.get(id);
const fresh = input && Date.now() - input.receivedAt < INPUT_TIMEOUT_MS;
```

---

### P1-12 · Ended rooms are never reset; "Play Again" joins a dead match
`TeamDeathmatchRoom.ts:263,550-562` · `GamePage.tsx:129-136`

`endMatch()` sets `phase = "ended"`, and `onTick` then returns immediately on every subsequent tick. The room is never locked, disposed, or reset. It is still discoverable, so `joinOrCreate("tdm")` matches it — which is exactly what `MatchEnd → handlePlayAgain → playSession++ → remount → new join` does. **Clicking "Play Again" reliably drops you into a frozen room** with the old scores and no simulation.

**Fix.** In `endMatch()`, call `this.lock()` immediately so no new player is matched in. Then `this.clock.setTimeout(…, POST_MATCH_MS)` to either fully reset state (scores → 0, phase → `warmup`, respawn everyone, `this.unlock()`) or `this.disconnect()` so every client re-matchmakes into a fresh room.

### P1-13 · Countdown does not abort when players leave
`TeamDeathmatchRoom.ts:210-214,229-243`

`onLeave` deletes the player and nothing else. If the room drops below `warmupPlayers` mid-countdown, the countdown continues and the match starts with one player. The phase also never returns to `waiting` when the room empties, so a room that everyone left sits in `warmup` or `in-progress` forever.

**Fix.** Add the inverse of `checkWarmup()` to `onLeave`: if `players.size < warmupPlayers` and `countdownRunning`, cancel it, reset `countdown`/`state.countdown` to 0, and set the phase back to `warmup` (or `waiting` at zero players).

### P1-14 · Red players stack on one spawn point
`TeamDeathmatchRoom.ts:172-175`

```ts
const team = blueCount <= redCount ? "blue" : "red";
const spawn = SPAWNS[team][blueCount % SPAWNS[team].length];
```

When `team === "red"`, the index is still derived from **`blueCount`**. Because the balancer alternates, `blueCount` is frequently identical for consecutive red joiners — multiple red players spawn on the same coordinates, inside each other.

**Fix.**

```ts
const count = team === "blue" ? blueCount : redCount;
const spawn = SPAWNS[team][count % SPAWNS[team].length];
```

The same bug pattern is worth checking on respawn (`:301` uses `s.deaths`, which is correct).

### P1-15 · StrictMode double-mount leaves ghost players in the room
`main.tsx:10` · `Game.ts:26-33` · `GameSocket.ts:223-230`

React StrictMode runs `GamePage`'s effect twice in dev. `createGame` calls `socket.connect()` **without awaiting it**, and the cleanup path calls `engine.dispose() → socket.leave()`, which does `await this.room?.leave()` — but `room` is still `null` while the join is in flight. The first connection therefore completes *after* its owner was disposed and **never leaves**, occupying a seat until Colyseus times it out.

**Fix.** Have `GameSocket` retain the connect promise and a `disposed` flag:

```ts
async leave() {
  this.disposed = true;
  await this.connectPromise?.catch(() => {});
  await this.room?.leave();
}
```

and bail out of `connect()`'s wiring if `disposed` became true while awaiting.

### P1-16 · Changing mouse sensitivity restarts the entire match
`GamePage.tsx:127`

`settings.sensitivity` is in the effect's dependency array. Dragging the sensitivity slider in the pause menu **disposes the renderer, destroys the Three.js scene, drops the socket and rejoins the server** — on every step of the drag. `GameEngine.applySettings()` exists specifically to avoid this and is only called at construction.

**Fix.** Remove `settings.sensitivity` from the deps and add a separate effect:

```ts
useEffect(() => {
  engineRef.current?.getEngine().applySettings({ sensitivity: settings.sensitivity });
}, [settings.sensitivity]);
```

### P1-17 · Client bullet impacts land on the wrong surface
`Weapon.ts:197-246`

Two defects in one function. It tests the ground plane **first and returns immediately** (`:204-211`), so any downward-angled shot at a wall reports a floor hit. It then returns the **first** intersecting AABB in list order rather than the nearest (`:221-242`), so impact effects appear on whichever box happens to be earliest in `colliders`, potentially behind the wall you shot.

**Fix.** Accumulate every candidate `t` (ground plus each box) and return the minimum.

---

### P1-18 · Direction sent to the server is not the ray the client fired
`Weapon.ts:153-160,169` · `GameEngine.ts:337-343`

The client raycasts from `camera.position` but reports `origin = muzzleWorld` (offset `(0.06, −0.05, −0.5)` in camera space) and `dir = normalize(hitPoint − muzzleWorld)`. Origin and direction come from **two different rays**. The parallax is small at range but significant at close quarters, so client and server disagree about exactly the shots that matter most.

**Fix.** Send `camera.position` and `camera.getWorldDirection()`. Use the muzzle position only as the visual start of the tracer. (Once P0-1 lands, the server reconstructs the origin anyway and only the direction matters.)

### P1-19 · GPU memory leaks in effects, remote players, and teardown
`Effects.ts:27-106,133-138` · `RemotePlayers.ts:70-88,110-118` · `GameEngine.ts:159-165,386-397`

- `muzzleFlash`, `bulletImpact` and `tracer` each allocate a **new geometry and material per shot** — at 600 RPM that's 10 muzzle flashes, 10 tracers and 40 spark meshes per second. `Effects.update` and `dispose` only call `scene.remove()`; nothing is ever `.dispose()`d, so the GPU buffers are never freed.
- `RemotePlayers.add` allocates two geometries and two materials per player; `remove` drops the scene reference without disposing them. A single respawn/rejoin cycle leaks.
- `GameEngine.dispose()` never disposes the map's geometries or materials, and **never removes the `resize` listener** added at `:165` — it holds a reference to the whole engine, so nothing is collectable after a remount.

**Fix.** Hoist shared geometries/materials to module constants, pool the particles, dispose everything in `dispose()`, and keep a handle to `onResize` for removal.

### P1-20 · Loose input validation on yaw/pitch; pitch is never clamped
`TeamDeathmatchRoom.ts:155-156`

```ts
yaw: isFinite(input.yaw) ? input.yaw : 0,
```

Global `isFinite` **coerces its argument**, so `isFinite("5")` and `isFinite(true)` are both `true`. A string or boolean therefore passes the guard and is assigned into a `@type("number")` schema field. Separately, pitch is never clamped server-side despite spec `0003` stating "clamped ±PI/2" — a client can send `pitch: 100` and the server will accept and broadcast it.

**Fix.**

```ts
yaw:   Number.isFinite(input.yaw)   ? normalizeAngle(input.yaw) : 0,
pitch: Number.isFinite(input.pitch) ? clamp(input.pitch, -PITCH_LIMIT, PITCH_LIMIT) : 0,
```

(Use the fixed `normalizeAngle` from P2-25 — the current one can hang.)

### P1-21 · No rate limiting anywhere
`apps/api/src/index.ts:20,35-41` · `TeamDeathmatchRoom.ts:147-167`

- `POST /auth/guest` is unauthenticated, unthrottled, and issues non-expiring tokens.
- Every distinct `sub` adds a permanent entry to the in-memory `profileSettings` Map (`:20`) with no eviction — a scripted loop grows it without bound until the process OOMs.
- The room accepts unlimited `"input"` and `"shoot"` messages per client per tick. The fire-rate check gates *damage*, not *work* — validation, normalization and the O(players) raycast still run per message.

**Fix.** `@fastify/rate-limit` on `/auth/guest`; `expiresIn` on tokens; a TTL/LRU cap on the settings map; and a per-client message budget in the room that disconnects clients exceeding, say, 120 messages/second.

---

### P1-22 · Guest usernames are not validated server-side
`apps/api/src/index.ts:36-37`

`(request.body as any)?.username` is written into the JWT unchecked, and from there into `client.auth.username`, the schema, the kill feed and the scoreboard shown to every player. React escapes markup so this is not XSS, but there is **no length cap, no charset restriction and no uniqueness check** — a 100 KB name, control characters, or a name identical to another player's are all accepted. The client's `maxLength={16}` (`Home.tsx:36`) is cosmetic; the API is the trust boundary.

**Fix.** A Fastify JSON schema on the route: `{ username: { type: "string", pattern: "^[A-Za-z0-9_-]{3,16}$" } }`.

---

### P1-23 · Dead players remain standing
`RemotePlayers.ts:90-108`

`update()` stores `player.alive` into `entry.last` and never reads it. Mesh visibility is never toggled, so a killed player's box stands upright at the point of death until the server respawns them 3 seconds later and teleports the mesh. The health bar also divides by a hardcoded `100` (`:106`) rather than `maxHealth`.

**Fix.** `entry.mesh.visible = player.alive;` in `update()`, and `player.health / PLAYER_MAX_HEALTH`.

---

### P1-24 · The riskiest code has no tests
`packages/*/src/*.test.ts`

12 unit tests exist, covering `clamp`/`lerp`/`normalizeAngle`, `PlayerInput` JSON shape, and weapon constant sanity. **`TeamDeathmatchRoom.ts` — 563 lines containing every finding in P0 and half of P1 — has zero unit tests.** The four integration scripts cover happy paths only (two clients join, one shoots the other, kill limit reached, warmup counts down). Nothing regression-tests shot validation, wall occlusion, team balance, spawn selection, phase transitions on leave, or input staleness.

**Fix.** Extract the pure logic — `raycastAABB`, `raycastPlayerCapsule`, `integrateMovement`, `validateShot` — into a new `packages/sim` consumed by the room, and unit-test it directly. Add `@colyseus/testing` room tests for join/leave/phase transitions. Every P0 above should land with a test that fails before the fix.

# Recommended fix order

## Themes worth noting

**The client is the more complete simulation.** Collision, ADS speed, spread and recoil all exist client-side and are absent server-side. For a project whose stated architecture is "server-authoritative", the authority is currently the weaker model — which is what makes P0-1 through P0-3 exploitable rather than merely inconsistent. Batch 2 is the structural correction; most of the rest is downstream of it.

**Test coverage is inverted.** The 12 existing tests cover `clamp` and constant sanity — code unlikely to be wrong. The 563-line room holding all the authority logic has none. Extracting pure functions is worth doing for testability alone, independent of the collision fixes.

**Specs are treated as write-once.** Five documented behaviors no longer match the code, including a message type (`"respawn"`) that was specified but never implemented and a phase (`warmup`) that was implemented but never specified. The `AGENTS.md` same-PR rule is the right policy; it needs CI or review enforcement to hold.
